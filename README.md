# blog_ant_org

Self-hosted [Ghost](https://ghost.org/) blog with [Remark42](https://remark42.com/)
comments, provisioned reproducibly on [Hetzner Cloud](https://www.hetzner.com/cloud)
with [OpenTofu](https://opentofu.org/). TLS via Caddy, transactional email via AWS SES,
nightly backups to S3.

- **Blog:** https://blog.ant.org
- **Comments:** https://comments.ant.org (GitHub login, moderated)
- **Image:** `ghcr.io/blowback/blog_ant_org` (Ghost + the `source-custom` theme)

---

## How it fits together

The guiding principle: **config rebuilds the machine; backups restore the data.**
A total loss of the server is recoverable by `tofu apply` (rebuilds the box from
this repo) followed by a restore from S3 (repopulates posts, images, comments).

```
                         ┌─────────────────────────────────────┐
   theme/ or Dockerfile  │  GitHub Actions  →  ghcr.io image    │
   change ──push──────▶  │  (.github/workflows/docker.yml)      │
                         └─────────────────────────────────────┘
                                          │ pulled at boot
                                          ▼
   deploy/ change ──push──┐    ┌────────────────────────────────┐
                          ├──▶ │  tofu apply  →  Hetzner server  │
   *.tf / cloud-init ─────┘    │  cloud-init: git clone + .env   │
                               │  docker compose up -d           │
                               └────────────────────────────────┘
                                          │ nightly 03:30
                                          ▼
                               ┌────────────────────────────────┐
                               │  backup.sh  →  S3 bucket        │
                               │  (mysqldump + volumes)          │
                               └────────────────────────────────┘
```

### Three change-types, three actions

| You changed…                              | Pipeline            | What to run                                   |
|-------------------------------------------|---------------------|-----------------------------------------------|
| `theme/**` or `Dockerfile`                | Image (GitHub Actions) | Push → wait for green build → then rebuild box |
| `deploy/**` (compose, Caddyfile, backup)  | Boot-time git clone | Push → `tofu apply -replace=hcloud_server.blog` |
| `*.tf`, `cloud-init.yaml.tftpl`           | OpenTofu            | `tofu apply` (reads local files)              |

Only the **image** pipeline is triggered by git. The OpenTofu pipeline reads your
local working files — but always commit close to applying so the repo reflects
what is deployed.

### Repo layout

```
.
├── *.tf                     # OpenTofu: server, firewall, SES, S3 backups
├── cloud-init.yaml.tftpl    # boot config: writes .env (base64), clones repo
├── terraform.tfvars         # secrets — GITIGNORED, never commit
├── terraform.tfvars.example # template for the above
├── Dockerfile               # FROM ghost:5-alpine + COPY theme
├── theme/source-custom/     # the Ghost theme (Remark42 embed lives in post.hbs)
└── deploy/                  # files cloned onto the box verbatim at boot
    ├── docker-compose.yml
    ├── Caddyfile
    ├── backup.sh
    └── blog-backup.cron
```

### What lives where (and why it matters for recovery)

- **Infrastructure** (server, software, theme *files*) → this repo + the ghcr.io
  image. Reproduced by `tofu apply`.
- **Content** (posts, uploaded images, the *active* theme choice, comments) → lives
  in MySQL and Docker volumes. Reproduced by **restore from backup** — it cannot
  live in config.
- **Secrets** (DB/SES/backup creds) → generated by OpenTofu, written only into
  `/opt/blog/.env` on the box and into local `terraform.tfstate`. Never in git.

## Day-to-day operations

All commands assume you are in the repo dir locally, or SSH'd to the box as root.
Set `BOX` to the current IP for convenience:

```bash
BOX=$(tofu output -raw server_ipv4)
```

### Rebuild the server from scratch

This destroys the box (and its volumes) and builds a fresh one from config.

```bash
# 1. Make sure deploy/ changes are on the remote the box will clone:
git ls-tree -r origin/main --name-only | grep '^deploy/'

# 2. Rebuild:
tofu apply -replace=hcloud_server.blog

# 3. Check the IP and repoint DNS if it changed:
tofu output server_ipv4
dig +short blog.ant.org
#    If different, update the `blog` and `comments` A records at No-IP.
#    Use the RELATIVE host field ("blog", "comments") — not the FQDN.

# 4. Confirm a clean boot:
ssh root@$BOX 'cloud-init status --long'          # want: status: done
ssh root@$BOX 'docker compose -f /opt/blog/docker-compose.yml ps'
```

On a fresh box the database is empty, so:
- Re-run the Ghost setup at `https://blog.ant.org/ghost` to create the admin user.
- **Design → activate `source-custom`** (the theme files are in the image, but the
  *active* choice is a DB setting — blank on a fresh box, or restored via backup).
- Comments come up GitHub-authed with you as moderator automatically (from `.env`).

> Caddy obtains certs only once the domains resolve to the box. After a DNS repoint
> it retries automatically; give it a minute. Check with:
> `ssh root@$BOX 'docker compose -f /opt/blog/docker-compose.yml logs caddy | grep -i certificate'`

### Change the theme

The theme is baked into the Docker image, so a theme change means rebuilding the
image, then running it.

```bash
# 1. Edit files under theme/source-custom/ (e.g. post.hbs for the comments embed).
# 2. Commit & push — this triggers the GitHub Actions build to ghcr.io:
git add theme/ && git commit -m "theme: ..." && git push
# 3. Wait for the Actions run to go green (Actions tab), then run the new image.
#    Either rebuild the box:
tofu apply -replace=hcloud_server.blog
#    …or pull-and-restart on the running box (faster, no data loss):
ssh root@$BOX 'cd /opt/blog && docker compose pull ghost && docker compose up -d ghost'
```

The running container does **not** auto-update when a new `:latest` is pushed — you
must `pull` + `up -d` (or rebuild) to pick it up.

To force an image rebuild without a code change (e.g. for a fresh `ghost:5-alpine`
base), add `workflow_dispatch:` to the workflow's `on:` block and use the
"Run workflow" button in the Actions tab.

### Change a deploy file (compose / Caddyfile / backup / cron)

These are cloned onto the box at boot — no image build involved.

```bash
# Edit deploy/<file>, then:
git add deploy/ && git commit -m "deploy: ..." && git push

# Apply to the RUNNING box without a full rebuild (idempotent with a fresh boot):
ssh root@$BOX 'cd /opt/blog/repo && git pull && \
  cp deploy/docker-compose.yml deploy/Caddyfile /opt/blog/ && \
  cp deploy/backup.sh /opt/blog/backup.sh && chmod 0750 /opt/blog/backup.sh && \
  cd /opt/blog && docker compose up -d'

# …or just rebuild the box, which clones the new files cleanly:
tofu apply -replace=hcloud_server.blog
```

## Backups

Nightly at 03:30 (`/etc/cron.d/blog-backup`), `backup.sh` dumps the Ghost MySQL
database and tars the `ghost_content` (uploaded images) and `remark42_data`
(comments) volumes into one timestamped bundle, and uploads it to the S3 bucket.
The bucket's lifecycle rule expires bundles after `backup_retention_days` (default
30). The backup IAM user has no `DeleteObject` permission — the box can write
backups but cannot erase history.

### Trigger a backup manually

```bash
ssh root@$BOX '/opt/blog/backup.sh'
# expect: "... backup ok: blog-backup-<timestamp>.tar (<size>)"
```

### List backups in S3

```bash
ssh root@$BOX 'set -a; . /opt/blog/.env; set +a; \
  docker run --rm -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_DEFAULT_REGION \
  amazon/aws-cli s3 ls "s3://$BACKUP_BUCKET/"'
```

### Restore from a backup

Restores data onto a running (typically freshly-rebuilt) box. Full steps in
[`deploy/RESTORE.md`](deploy/RESTORE.md). Summary:

```bash
ssh root@$BOX
cd /opt/blog
set -a; . ./.env; set +a

# 1. Pick & pull a bundle (using the aws-cli container):
docker run --rm -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_DEFAULT_REGION \
  -v /tmp:/work amazon/aws-cli s3 cp \
  "s3://$BACKUP_BUCKET/blog-backup-YYYYMMDDTHHMMSSZ.tar" /work/restore.tar
mkdir -p /tmp/restore && tar xf /tmp/restore.tar -C /tmp/restore

# 2. Stop the app containers (keep mysql up):
docker compose -f /opt/blog/docker-compose.yml stop ghost remark42

# 3. Restore the database:
gunzip -c /tmp/restore/ghost-db.sql.gz | \
  docker compose -f /opt/blog/docker-compose.yml exec -T mysql \
  mysql -uroot -p"$MYSQL_ROOT_PASSWORD" ghost

# 4. Restore the volumes:
docker run --rm -v blog_ghost_content:/data -v /tmp/restore:/in alpine \
  sh -c 'rm -rf /data/* && tar xzf /in/ghost-content.tar.gz -C /data'
docker run --rm -v blog_remark42_data:/data -v /tmp/restore:/in alpine \
  sh -c 'rm -rf /data/* && tar xzf /in/remark42-data.tar.gz -C /data'

# 5. Bring the app back:
docker compose -f /opt/blog/docker-compose.yml up -d ghost remark42
rm -rf /tmp/restore /tmp/restore.tar
```

After restore: posts, images, comments, and the active `source-custom` theme all
return (the theme choice rode along in the DB). The Remark42 admin ID still matches
because `REMARK_SECRET` is stable across a server `-replace`.

### Test the round trip

"I have backups" and "I have recovered from a backup" are different claims. Once you
have content worth the confidence, prove it once: make a throwaway post, run a
backup, `tofu apply -replace=hcloud_server.blog`, restore, and confirm the post and
its comments come back.

## Gotchas worth remembering

- **DNS host field at No-IP is relative.** Enter `blog` / `comments`, not the FQDN,
  or the zone gets doubled. TXT records (SPF/DMARC) are auto-quoted — enter the bare
  value.
- **A `-replace` changes the IP.** The volumes are destroyed and the IPv4 changes;
  repoint DNS after every rebuild (unless you add a Hetzner Floating IP).
- **The box clones the repo at boot.** `deploy/` changes must be pushed to `origin/main`
  *before* a rebuild, or the clone pulls stale/missing files.
- **No `awscli` on the host.** Ubuntu 24.04 dropped the apt package; the backup and
  restore use the `amazon/aws-cli` Docker image instead. `packages:` only installs
  `cron` and `git`.
- **`cloud-init.yaml.tftpl` has exactly one inline file** (`.env`, base64-encoded).
  Everything else is a normal file in `deploy/`. Keep it that way — embedding
  multi-line content in the template reintroduces the YAML-indentation fragility.
- **State is precious and unencrypted.** `terraform.tfstate` holds every secret in
  plaintext and is the only record of what OpenTofu manages. It is gitignored; do not
  lose it. Consider a remote encrypted backend if this grows.
- **If you ever make the repo private**, the ghcr.io package goes private too (it
  inherits repo access), and the box's anonymous image pull breaks — give the box a
  `read:packages` token or set the package explicitly public.
- **If you ever `-replace` the `random_password` resources**, `REMARK_SECRET`
  regenerates, every Remark42 user ID rehashes, and you must reset `ADMIN_SHARED_ID`.

## Prerequisites for a clean checkout

- OpenTofu, an `hcloud` token, AWS creds for the bootstrap `terraform-blog` user
  (needs IAM + SES + S3 permissions).
- `cp terraform.tfvars.example terraform.tfvars` and fill in: `hcloud_token`,
  `ssh_public_key`, `ssh_source_cidr`, domains, `acme_email`, `gh_cid`/`gh_csec`,
  `remark_admin_id`.
- DNS A records for `blog` and `comments` at your provider.
- `tofu init && tofu apply`.
